The Problem

Cloudflare's CLI assumes a desktop

Wrangler is excellent — on a laptop. On an Android phone running Termux, its assumptions break one by one.

✗

OAuth callbacks fail

wrangler login tries to reach localhost:8976 — unreachable inside PRoot. You end up copying device codes by hand.

✗

11–18 seconds per command

Every Wrangler invocation spawns Node afresh through PRoot's syscall translation. Re-authentication alone costs 25 seconds.

✗

Invisible deployment target

Deploy has no visible account, worker, or environment. One wrong command and you have shipped to production.

✗

Termux ↔ PRoot friction

Every command needs proot-distro login debian. State lives in two places. Nothing carries across boundaries.

What It Does

Six commands. All of Cloudflare deployment.

$ wrangler-tui auth

Opens your browser via Termux, pre-fills the device code, waits for approval, caches the result for 5 minutes.

$ wrangler-tui init

Create a new Worker project — minimal offline scaffold or the official create-cloudflare template.

$ wrangler-tui deploy

Preflight dry-run, visible deployment target, typed worker name confirmation, then live deploy. Exit code is the source of truth.

$ wrangler-tui tail

Stream logs from your deployed Worker. Ctrl-C stops cleanly. No orphaned processes.

$ wrangler-tui logout

Clears the session and verifies with wrangler whoami. Never claims success without proof.

$ wrangler-tui test

Runs 6 checks against a mock project: Node version, Wrangler presence, auth status, project detection, dry-run deploy.

How It Works

One command, two environments

You type wrangler-tui once. A small shim handles the Termux-to-PRoot hop, starts the URL bridge if needed, and passes through to the Node.js application inside Debian. The application itself has zero Termux-specific code.

You type$ wrangler-tui deploy
↓
Termux shim$PREFIX/bin/wrangler-tui
starts URL bridge, hops into PRoot
↓
PRoot Debian/usr/local/bin/wrangler-tui
Node.js application, 14 modules
↓
Cloudflare's own binaryspawn('wrangler', [...args])
↓
Cloudflareyour Worker, deployed

Every Cloudflare operation goes through Wrangler's own executable. Nothing is reimplemented. The tool composes; it does not replace.

Install

Three commands. One-time.

Requires Termux (from F-Droid, not Play Store), ~1.5 GB free storage, and network access for the initial install.

$ git clone https://github.com/SANDMAN-CORPORATION/wrangler-tui $ cd wrangler-tui $ bash setup.sh

The setup script installs Node.js, Wrangler, and the launcher shim. It is idempotent — safe to run twice.

Usage

From any Wrangler project directory

# First time: authenticate $ wrangler-tui auth # Create a new project $ wrangler-tui init # Deploy a project $ wrangler-tui deploy # Or from any directory, without cd $ wrangler-tui deploy --dir ~/my-worker # Stream remote logs $ wrangler-tui tail

See the full README for flags, environment variables, and known limitations.

What It Does Not Do

Limitations, stated plainly

Every tool has limits. These are documented so you are not surprised.

Local wrangler dev does not work.The bundled workerd runtime cannot initialize under PRoot's virtual-address configuration. Local development must run on a desktop.
Auth cache TTL is 5 minutes.If you pause for more than 5 minutes between commands, you pay a 25-second re-authentication. This will be tuneable in a future release.
Wrangler's own startup is 11–18 seconds.Every spawn is expensive through PRoot. Three caches reduce the number of spawns, but each spawn is still slow. This is not fixable in the tool.
No resource management yet.KV, D1, R2, and secrets management are post-MVP. Use wrangler directly for these.
First release, no external users yet.104 tests pass on the author's device. It has not been tested by anyone else. First external use is the next milestone.
